# NSW Electricity Price & Demand — Time Series Dates with pandas (and Polars)

A small, self-contained project about **handling time series date data** with
pandas, plus a Polars equivalent and a benchmark that compares both engines on
the identical pipeline. Everything runs against the real AEMO *price and demand*
data for the **NSW1** region of Australia's National Electricity Market,
January 2018 – June 2023: **66 monthly CSV files, 248,592 rows**.

## Highlights

- **`main.py`** — the pandas workflow: read, parse dates, extract date
  components, resample to weekly sums, and compute row-over-row differences.
- **`main_polars.py`** — the same operations using Polars **lazy** evaluation
  (`scan_csv` → query plan → `collect()`).
- **`compare_performance.py`** — proves both engines return identical results,
  *then* benchmarks them phase by phase (best/median of N runs).
- **`read_kaggle_data.py`** — fetches the Kaggle dataset without credentials and
  reads the full 2018-01 … 2023-06 range.

## The data

Source: [NSW, AUS, Electricity Price & Demand 2018-2023](https://www.kaggle.com/datasets/joebeachcapital/nsw-australia-electricity-demand-2018-2023)
— a mirror of AEMO's aggregated *price and demand* files, one per month, also
published directly at
`https://aemo.com.au/aemo/data/nem/priceanddemand/PRICE_AND_DEMAND_<YYYYMM>_NSW1.csv`.

| Property | Value |
| --- | --- |
| Files | 66: `PRICE_AND_DEMAND_201801_NSW1.csv` … `PRICE_AND_DEMAND_202306_NSW1.csv` |
| Rows | 248,592 |
| Columns | `REGION`, `SETTLEMENTDATE`, `TOTALDEMAND`, `RRP`, `PERIODTYPE` |
| Coverage | 2018-01-01 00:30:00 → 2023-06-28 00:00:00 |
| Constants | `REGION = NSW1`, `PERIODTYPE = TRADE`, no duplicate timestamps |
| Size on disk | 12 MB in `data/` |
| Provenance | `PRICE_AND_DEMAND_201801_NSW1.csv` is sha256-identical to AEMO's original (`fe8a1535…d683`) |

**The sampling cadence changes mid-dataset.** Through 2021-09 rows are 30-minute
intervals; from 2021-10 onwards AEMO publishes 5-minute data (the 5-minute
settlement change). Measured across the whole range: 182,880 five-minute steps
and 65,711 thirty-minute steps, which sum to 248,591 = `rows − 1` — so there are
**no gaps and no duplicate timestamps** anywhere.

### Getting the data

```bash
uv run python read_kaggle_data.py                 # download + extract if needed, then read
uv run python read_kaggle_data.py --force-download
uv run python read_kaggle_data.py --rows 10       # rows to show at each end
```

The program calls Kaggle's public download endpoint
(`https://www.kaggle.com/api/v1/datasets/download/<slug>`), which works **without
an API token** for a public dataset, extracts the CSVs into `data/`, and then
verifies that all 66 monthly files are present (downloading again if any are
missing). The official alternatives — the Kaggle CLI
(`kaggle datasets download -d joebeachcapital/nsw-australia-electricity-demand-2018-2023`)
and `kagglehub.dataset_download(...)` — require an API token from
<https://www.kaggle.com/settings/account>.

## Usage

### 1. `main.py` — the pandas workflow

```bash
uv run python main.py
```

Reads **every** CSV in `data/` (glob `PRICE_AND_DEMAND_*.csv`, sorted by file
name) with the pyarrow engine, concatenates the frames, sorts by
`SETTLEMENTDATE`, and then:

1. prints the file count, row count, column list and the first five rows;
2. prints the dtype of `SETTLEMENTDATE`;
3. extracts `YEAR`, `MONTH`, `DAY` with the `.dt` accessor;
4. resamples weekly `TOTALDEMAND` sums with `resample("1W")`;
5. adds `MONTH_DIFFERENCE` from `MONTH.diff()`;
6. adds `TIME_DIFFERENCE_HOURS` and `TIME_DIFFERENCE_MINUTES` from
   `diff() / pd.Timedelta(...)`.


### 2. `main_polars.py` — the same operations, lazily

```bash
uv run python main_polars.py
```

`build_plan()` returns a `LazyFrame` that scans all 66 files and parses
`SETTLEMENTDATE` with `str.to_datetime(...)`; **nothing is read until
`.collect()`**. The operations are functions over a `LazyFrame`
(`with_date_components`, `weekly_demand`, `with_month_difference`,
`with_time_differences`), which is what lets the benchmark reuse them.

A `LazyFrame` is a *query description*, not cached data, so each `.collect()`
re-executes the whole plan and re-reads the CSVs. Collect once — or reuse an
already collected frame via `.lazy()` — when you don't want that.

A multi-file scan gives no row-order guarantee, so the plan ends with
`.sort("SETTLEMENTDATE")`; the sort stays lazy and is required for the
`diff()`-based columns to be meaningful.

### 3. `compare_performance.py` — equivalence first, then speed

```bash
uv run python compare_performance.py                  # 7 runs, 2 warm-ups
uv run python compare_performance.py --repeat 25 --warmup 3
```

The result check runs *before* any timing is reported, comparing **whole
columns** between the engines (row count, dtype, all five data columns, the three
derived columns, and all 287 weekly buckets — labels *and* sums). If anything
differs it prints `RESULTS DIFFER` and exits non-zero instead of publishing
misleading numbers.

```text
Result check (both engines must agree before timings are compared):
  [PASS] row count                    pandas=248592 polars=248592
  [PASS] SETTLEMENTDATE is datetime   pandas=datetime64[s] polars=Datetime(time_unit='us', time_zone=None)
  [PASS] column REGION                whole column
  ...
  [PASS] weekly bucket labels         287 buckets, first=2018-01-07 last=2023-07-02
  [PASS] weekly TOTALDEMAND sums      first=2683318.69

  => all results are identical
```

### 4. `read_kaggle_data.py` — fetch and read the whole dataset

```bash
uv run python read_kaggle_data.py --rows 5
```

Downloads the monthly files when they are missing, reads all 66 of them, and
prints the shape, date range, distinct regions, duplicate-timestamp count,
observed step sizes, rows per year, dtypes and the first/last rows — see
[Getting the data](#getting-the-data).

## Benchmark results

All 66 files (248,592 rows) on this machine, `--repeat 7 --warmup 2`; **best**
and **median** of the timed runs, in milliseconds:

| Phase | pandas best | pandas med | Polars best | Polars med | Polars speedup |
| --- | ---: | ---: | ---: | ---: | ---: |
| load + parse dates | 87.098 | 88.422 | 8.925 | 10.041 | 9.76× |
| extract YEAR/MONTH/DAY | 5.853 | 5.877 | 10.047 | 11.009 | 0.58× |
| weekly TOTALDEMAND sums | 51.971 | 52.160 | 7.914 | 10.267 | 6.57× |
| row differences (month / hours / minutes) | 12.266 | 12.377 | 13.128 | 15.230 | 0.93× |
| full pipeline (load + all operations) | 160.337 | 164.849 | 15.722 | 17.503 | 10.20× |
| Polars plan build only (no `collect()`) | – | – | 0.0156 | 0.0162 | – |

How to read this:

- **Each Polars *phase* row re-reads and re-parses all 66 CSVs** (≈9 ms of I/O),
  because every `.collect()` re-executes the whole plan, while pandas works on a
  frame that is already in memory. That is why `extract YEAR/MONTH/DAY` and
  `row differences` appear to favour pandas — it is an artefact of the phase
  split, not of the engines.
- **The like-for-like number is the full pipeline** (one plan, one `collect()`):
  Polars is **10.2× faster**. The advantage grows with the data size — on the
  original single 67 KiB file the same pipeline measured 2.1×–2.3×.
- Planning is essentially free (**0.016 ms**); the work happens at `collect()`.
- Timings exclude interpreter start-up and library imports (they occur before any
  timer starts). Whole-script wall time *including* imports: `main.py` ≈ **0.78 s**,
  `main_polars.py` ≈ **0.43 s**.

## Notes and gotchas

- **Weekly buckets have to be aligned deliberately.** pandas `resample("1W")`
  (W-SUN) splits a week into a **left-closed Monday→Monday** window **labelled with
  the closing Sunday** — verified from per-bucket row counts (335, then 336 …).
  Polars labels a window by its *start* edge, so the equivalent is
  `group_by_dynamic(every="1w", closed="left", label="left", start_by="monday")`
  followed by `.dt.offset_by("6d")` on the window label. With that, both engines
  agree on **all 287 buckets' labels and sums**.
- **The first and last weekly buckets are partial**: the data starts
  2018-01-01 00:30 and ends 2023-06-28 00:00, so the buckets `2018-01-07` and
  `2023-07-02` cover less than a full week.
- **`TIME_DIFFERENCE_HOURS` is not uniform**: 0.5 h through 2021-09, then 0.0833…
  (5 minutes) from 2021-10. Row-count statistics are not comparable across that
  boundary; time-based resampling is unaffected.
- **`MONTH_DIFFERENCE` is 0.0** everywhere except at month boundaries. That is
  what `MONTH.diff()` measures — it only becomes informative over a multi-month
  range like this one.
- **Polars renders large floats in scientific notation** (e.g. `2.6833e6` where
  pandas prints `2683318.69`). The values are identical — the equivalence check
  proves it — only the rendering differs.
- `main.py` re-converts `SETTLEMENTDATE` with `pd.to_datetime(...)` even though
  the loader has already parsed it (a harmless no-op kept in place to preserve
  the original tutorial flow).

## Verification performed

Checked on 2026-09-20 (Arch Linux under WSL2, uv 0.12.10):

- `main.py`, `main_polars.py` and `compare_performance.py` all exit `0`;
  `py_compile` passes for all four programs.
- `compare_performance.py` reports **14/14 checks PASS** — whole-column
  comparisons (~2.5 M value comparisons) plus all 287 weekly buckets.
- Result integrity: `cat data/*.csv | wc -l` = 248,658 lines = 248,592 rows
  + 66 headers, matching the DataFrame row count; no duplicate timestamps; every
  consecutive pair exactly 5 or 30 minutes apart.
- Provenance: the sha256 of `data/PRICE_AND_DEMAND_201801_NSW1.csv` matches
  AEMO's original file exactly.
- `read_kaggle_data.py` is idempotent (a second run re-uses the files on disk)
  and fails loudly when the dataset is incomplete.
- The equivalence checker was negative-controlled
  (`values_equal([1, 2], [1, 3])` → `False`; NaN ↔ null treated as equal), so the
  PASS results are meaningful rather than vacuous.
